# Chat E2EE Tickets

Сквозное шифрование сообщений чата. Модель: **комнатная парольная фраза**
(юзеров/аккаунтов в системе нет). Сервер хранит только шифротекст и не
участвует в криптографии.

Источник решений: обсуждение 2026-08, проверено живым WebSocket-клиентом
(`wss://erdmko.dev/ws/chat/{room}`, protobuf-фреймы).

## Execution Order

1. `E2EE-00` Contract Freeze: `body` → `bytes`
2. `E2EE-10` Server Storage: BLOB-миграция и серверная валидация
3. `E2EE-20` Crypto Core (TS): KDF + AES-GCM модуль
4. `E2EE-30` Message Flow: интеграция в отправку/приём/UI
5. `E2EE-40` Attachments: шифрование файлов
6. `E2EE-50` Stability & Security: e2e-тесты, аудит утечек, документация

## Dependency Map

- `E2EE-00` -> none
- `E2EE-10` -> `E2EE-00`
- `E2EE-20` -> none (можно параллельно с `E2EE-10`)
- `E2EE-30` -> `E2EE-10`, `E2EE-20`
- `E2EE-40` -> `E2EE-30`
- `E2EE-50` -> `E2EE-30`, `E2EE-40`

## Ключевые архитектурные решения

1. **Парольная фраза комнаты** — единственный секрет. Передаётся участникам
   вне чата. Аккаунтов нет, поэтому per-user ключи (X25519/ECDH) избыточны.
2. **KDF**: PBKDF2-SHA-256, 600 000 итераций, соль детерминирована от slug
   комнаты → все участники выводят одинаковый ключ без обмена ключами.
3. **Шифр**: AES-256-GCM через нативный WebCrypto. Ноль npm-зависимостей
   (в проекте нет runtime deps, только devDependencies — сохраняем это).
4. **Сервер не меняется криптографически**: он по-прежнему просто кладёт
   блоб в SQLite. Все изменения на его стороне — типы и лимиты длин.
5. **Forward secrecy отсутствует** (осознанно, v1): компрометация фразы =
   чтение истории. Зафиксировано в документации; апгрейд-путь — MLS/openmls.
